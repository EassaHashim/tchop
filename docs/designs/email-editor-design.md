## Problem Statement

tchop.io editors cannot customize transactional or system emails themselves. When a customer wants to change email copy (subject lines, body text, CTAs) or match their brand (logo, colors, fonts), they file a support ticket and the tchop team makes the change manually. This doesn't scale, creates friction during onboarding, and makes emails the one touchpoint where the white-label promise breaks down.

## Demand Evidence

Customers actively file support tickets requesting email copy changes and brand alignment. This is not a hypothetical need. The manual workflow already exists, confirming repeated demand. Every new customer onboarding likely surfaces this gap when their branded app sends generic-looking system emails.

## Status Quo

Today: customer files a support ticket requesting an email change. A tchop team member manually edits the template or config. The customer can't preview the result themselves. Turnaround depends on team availability. Each new customer means another round of manual setup. The emails are the only part of the tchop experience that doesn't feel white-labeled out of the box.

## Target User & Narrowest Wedge

**Target user:** The channel editor or organisation admin who manages day-to-day content and settings in the tchop dashboard. They already configure branding, push notifications, and channels. Emails are the gap in their control.

**Narrowest wedge:** A structured field editor with live preview for transactional emails. Editors can change copy (subject, headline, body, CTA, footer) and brand settings (logo, primary color, font) for each email type. No drag-and-drop, no custom layouts. But a real-time preview that shows the actual rendered email as they edit.

## Constraints

- Must integrate into the existing tchop dashboard (React-based)
- Email HTML must render correctly across major email clients (Gmail, Outlook, Apple Mail)
- Changes are scoped per-organisation (each org sees their own templates)
- Must support EN and DE content (tchop is bilingual)
- Cannot break existing email delivery pipeline
- Must be self-service: zero support tickets for standard customizations

## Premises

1. Editors need self-service control over both email copy AND visual branding. The team currently handles this manually via support tickets.
2. The editor lives as a dedicated page in the existing dashboard, not a separate app.
3. Scope covers transactional emails (welcome, password reset, invite, etc.) AND potentially other email types (digests, notifications).
4. Email is table-stakes infrastructure. Customers expect white-label control over emails the same way they expect it for the app itself.

## Approaches Considered

### Approach A: Template Variable Editor (Minimal Viable)

A dashboard page listing all email types. Each opens a form with editable fields (subject, headline, body, CTA, footer) plus brand settings (logo, color, font). No visual preview. Structured fields populate server-side templates.

- **Effort:** M
- **Risk:** Low
- **Pros:** Ships fast. Hard to break. Covers actual requests.
- **Cons:** No layout flexibility. Feels like settings, not an editor.

### Approach B: Full WYSIWYG Block Editor (Ideal Architecture)

Visual email editor with drag-and-drop blocks (header, text, image, button, divider, footer). Live preview. Uses MJML + React block editor or an SDK (Unlayer, Bee, Stripo). Full creative freedom.

- **Effort:** L
- **Risk:** Medium (email client rendering complexity)
- **Pros:** Maximum flexibility. Competitive differentiator. Extensible to newsletters.
- **Cons:** 3-4x more engineering. Email client testing is a discipline. Risk of broken emails.

### Approach C: Structured Fields + Live Preview (Hybrid)

Structured fields like Approach A, but with a real-time email preview panel showing the rendered email as the editor types. Brand settings auto-applied. No drag-and-drop, but editors see exactly what recipients will see. This is the pattern Stripe and Linear use.

- **Effort:** M
- **Risk:** Low
- **Pros:** Feels like a real editor. Impossible to break layout. Clear upgrade path.
- **Cons:** No custom layout flexibility. Preview must match email client rendering.

## Recommended Approach

**Approach C: Structured Fields + Live Preview.**

Delivers the polished editor experience customers expect while shipping nearly as fast as the minimal version. The live preview transforms a settings page into something editors enjoy using. The structured data model from day one keeps the door open for block editing later.

### Upgrade Path

- **Phase 1:** Structured fields + live preview for all email types.
- **Phase 2:** Selective block editing for high-flexibility email types (digests, roundups, event announcements). Add `templateMode: "structured" | "blocks"` per email type.
- **Phase 3:** Block editing as default for new email types. Migrate old types incrementally.

### Key Architectural Decision

Store email content as **structured data** (not raw HTML) from day one. Whether the editor uses structured fields or drag-and-drop blocks, the backend receives a content model that renders to HTML at send time. This means no data migration when upgrading the editor -- only the UI changes.

## Open Questions

1. How many distinct email types does tchop currently send? (Affects scope of initial build)
2. Are email templates currently per-organisation or global? What's the storage/retrieval model?
3. Which email rendering engine is used today? (MJML, custom HTML, third-party service?)
4. Should editors be able to send test emails from the preview?
5. Who controls email customization: org admins only, or also channel editors?
6. How does bilingual content work -- separate templates per language, or one template with language variants?

## Success Criteria

- Zero support tickets for standard email copy/branding changes after rollout
- Editors can customize and preview any transactional email in under 5 minutes
- Emails render correctly in Gmail, Outlook, and Apple Mail
- Every org's emails match their dashboard brand settings by default (auto-populated from existing brand config)

## Dependencies

- Existing dashboard framework (React)
- Current email template system and delivery pipeline
- Organisation-level brand settings (logo, colors, fonts -- already exist in dashboard)
- Backend API for storing/retrieving per-org email templates
