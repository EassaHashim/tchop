## Problem Statement

tchop.io clients (starting with AOK Plus, healthcare enterprise) need to create, promote, and manage events within their branded communication apps. Today there is no event functionality in tchop -- clients cannot announce events, collect RSVPs, manage capacity, or give users a calendar view of upcoming activities. Staffbase (primary competitor for internal comms) already offers an Event Registration Plugin. This is a client-requested feature with competitive parity implications.

## Demand Evidence

- AOK Plus (healthcare enterprise, ICP 1) explicitly requested event functionality for their employee app
- Staffbase offers Event Registration Plugin as a standard feature -- tchop clients are comparing capabilities
- No observed end-user behavior yet (client comms team request, not validated through user observation)
- AOK Plus has a specific cross-channel challenge: executives need to see events from both the general employee channel and the executive-only channel

## Status Quo

Currently, AOK Plus and other clients have no native way to handle events in tchop. Workarounds would involve:
- Long Post cards with event details (no RSVP capability)
- Poll cards as fake RSVPs (no capacity management, no waitlist, no calendar)
- Manual attendance tracking in external spreadsheets
- Push notifications sent manually for event reminders

The status quo is: events happen outside the app entirely, or they're announced as static content with no interactivity.

## Target User & Scope

**Primary user:** Admin/Editor at enterprise client (internal comms team) who creates and manages events
**End user:** Employee (Reader) who discovers, RSVPs, and attends events
**Scope:** Event awareness + RSVP + waitlist layer. tchop handles discovery, registration, and reminders. Actual event logistics (room booking, catering, agenda) stay in external tools. CSV export is the handoff mechanism.

## Constraints

- Must work within tchop's existing card-based architecture (Organisation > Channel > Mix > Card)
- Must support native iOS (Swift), Android (Kotlin), and React web
- Must be backward-compatible (old app versions hide unknown card types)
- Must be deployable behind a per-organisation feature flag
- All migrations must be additive (no destructive schema changes)
- Event card inherits existing card features: comments, reactions, bookmarks, tags, categories, search, author attribution

## Premises

1. **Events are card type #12** -- they live in mixes like any other card. A dedicated "Event Feed" tab is an alternative approach to discuss with the dev team (see Architecture Decision ADR-1 below).
2. **Scope stops at RSVP + waitlist.** tchop is the awareness/registration layer. Event logistics stay external. CSV export is the handoff.
3. **Cross-channel aggregation is Phase 2.** AOK Plus executives seeing events from multiple channels in one view is deferred. "My Events" provides a user-scoped cross-channel view (only events the user is attending/waitlisted for, queried by userId -- not a channel-scan aggregation). Full org-level calendar aggregation across channels is Phase 2.
4. **Recurring events are out of scope** for v1. Clients create individual event cards per occurrence.
5. **No end-user observation yet.** This is driven by client request and competitive pressure, not validated user behavior. The use case document should surface assumptions clearly.

# Part 1: Use Cases

## UC-1: Admin Creates an Event

**Actor:** Channel Admin or Editor (via CMS dashboard)
**Precondition:** User has admin/editor role in the target channel. Event feature flag is enabled for the organisation.

**Main Flow:**
1. Admin navigates to a mix in the CMS dashboard
2. Admin clicks "Add Content" and selects "Event" card type
3. Admin fills in event fields:
   - **Headline** (required) -- event title, max 360 chars
   - **Description** (optional) -- rich text event description
   - **Event Start Date/Time** (required) -- with timezone
   - **Event End Date/Time** (optional) -- with timezone
   - **Location** (optional) -- free text, tappable as map link if address detected
   - **Cover Image** (optional) -- using existing media upload system
   - **Capacity** (optional) -- max attendees, null = unlimited
   - **Registration Deadline** (optional) -- always defaults to event start time if not explicitly set (attend/unattend is always locked at some point)
   - **Show Attendees** (optional) -- toggle to display attendee avatars on card, default: on
4. Admin saves as draft, schedules, or publishes immediately
5. Default tags (if configured on the mix) are auto-assigned
6. Optional: auto-push notification fires if enabled on the mix

**Acceptance Criteria:**
- [ ] All field validations enforce types and limits
- [ ] Event start date must be in the future at creation time
- [ ] Event end date must be after event start date (if provided)
- [ ] Registration deadline must be before or equal to event start date (if provided)
- [ ] Capacity must be a positive integer or null
- [ ] Card is visible in feed immediately after publishing
- [ ] Feature flag OFF = Event card type not available in "Add Content"

**Edge Cases:**
- What if an admin sets capacity to 0? (Should be prevented -- minimum capacity = 1 if set)
- What if an admin edits start date to the past after publishing? (Should be prevented)
- What if an admin changes capacity below current attendee count? (No retroactive removal -- existing attendees stay, new RSVPs blocked)

## UC-2: User Discovers Events in Feed

**Actor:** Reader (app user, employee)
**Precondition:** User has access to the channel containing the event card

**Main Flow:**
1. User scrolls the feed in the app (web, iOS, or Android)
2. Event card appears in the feed with teaser view:
   - Cover image (if set)
   - Event title
   - Date/time (formatted in user's local timezone)
   - Location (if set)
   - Attendee count / capacity indicator (e.g. "12/50 attending")
   - Attendee avatar row (first 3-5 profile pics, if showAttendees enabled)
   - Attend button (or "Join Waitlist" if full, or hidden if past/locked)
3. User taps the card to open the detail view

**Acceptance Criteria:**
- [ ] Event card renders correctly in all three teaser styles (where applicable)
- [ ] Date/time shown in user's local timezone
- [ ] Location is tappable -- opens Apple Maps (iOS) / Google Maps (Android) / Maps link (web)
- [ ] Attendee count updates via polling (30s interval on feed view, 10s on event detail view). Live WebSocket subscription is not required for v1 -- polling is sufficient given expected event volumes. TBD with dev team if subscription is simpler to implement.
- [ ] Past events show greyed-out cover image + "This event has ended" badge
- [ ] Attend button is hidden for past events
- [ ] Old app versions that don't know the Event card type hide it entirely (backward compatibility)

**Edge Cases:**
- Event with no cover image: display a branded date-stamp placeholder showing the event date in large format (day number + month abbreviation) over the organisation's primary brand color. This ensures visual consistency across iOS, Android, and web without requiring a cover image.
- Event spanning multiple days (show start date -- end date range)
- Event starting in < 1 hour: defer "Starting soon" indicator to Phase 2. Not required for v1.

## UC-3: User Attends an Event (RSVP)

**Actor:** Reader
**Precondition:** Event is published, not past, registration not closed

**Main Flow:**
1. User taps "Attend" on the event card (from feed teaser or detail view)
2. System checks:
   - Is registration still open? (deadline not passed, event not started)
   - Is there capacity remaining?
3. **If capacity available:** User status set to ATTENDING, attendee count incremented atomically
4. **If capacity full:** User status set to WAITLISTED, waitlist count incremented, user sees waitlist position
5. User receives confirmation:
   - Visual feedback on the card (button changes to "Attending" / "On Waitlist #N")
   - Optional: .ics calendar file download prompt

**Acceptance Criteria:**
- [ ] Atomic capacity check prevents race conditions (two users clicking simultaneously when 1 spot remains)
- [ ] Double-tap is idempotent -- returns current status, no duplicate entry
- [ ] Attend/unattend debounced at 1s minimum
- [ ] User can only attend for themselves (server-side userId = currentUser.id enforcement)
- [ ] Waitlist position is visible to the waitlisted user
- [ ] Attend action is blocked after registration deadline (which always defaults to event start time if not explicitly set)

**Edge Cases:**
- User on slow connection taps "Attend" twice -- must not create duplicate
- User tries to attend from two devices simultaneously -- must be idempotent
- Admin reduces capacity after user is already attending -- attending users are NOT removed
- Event with no capacity limit -- everyone is ATTENDING, no waitlist logic needed
- Network failure during attend/unattend: use pessimistic UI (wait for server confirmation before updating button state). On failure, show inline error "Could not register. Try again." Do NOT use optimistic updates for RSVP -- capacity state is critical and must reflect server truth.

## UC-4: User Cancels Attendance (Un-attend)

**Actor:** Reader
**Precondition:** User is currently ATTENDING or WAITLISTED

**Main Flow:**
1. User taps "Attending" button (which acts as toggle) or explicit "Cancel" action
2. System removes user from attendee/waitlist
3. **If user was ATTENDING and a waitlist exists:** Next waitlisted user is automatically promoted to ATTENDING
4. Promoted user receives push notification: "A spot opened up! You're now attending [Event Name]"
5. Attendee/waitlist counts updated atomically

**Acceptance Criteria:**
- [ ] Unattend is blocked after event starts (or after registration deadline, if set)
- [ ] Waitlist promotion happens as a background job (not blocking the unattend response)
- [ ] Promoted user receives push notification
- [ ] If promoted user has no valid push token or is deactivated, promotion still happens (status changes to ATTENDING) but push notification is silently skipped. System proceeds to promote the next waitlisted user only if the current candidate's account is deactivated/deleted -- not merely because push delivery failed.
- [ ] Waitlist promotion is FIFO (first waitlisted = first promoted)

**Edge Cases:**
- User unattends, triggering promotion, but the promoted user's push fails -- promotion still stands, push is best-effort
- Multiple users unattend simultaneously -- each triggers independent promotion. Double-promotion is prevented by an atomic state transition in the DB: `UPDATE attendees SET status = 'ATTENDING' WHERE id = ? AND status = 'WAITLISTED'` -- only one concurrent job can succeed on a given waitlisted user row.
- Last waitlisted user unattends -- nothing to promote, just decrement count
- User unattends and re-attends quickly -- should work, but subject to 1s debounce

## UC-5: User Downloads Calendar File (.ics)

**Actor:** Reader
**Precondition:** User has access to the event (any channel member can download .ics -- not restricted to ATTENDING users, since adding to calendar is a discovery/planning action)

**Main Flow:**
1. User taps "Add to Calendar" action on the event detail view (available to all users who can see the event, regardless of RSVP status)
2. System generates .ics file with event details (title, date/time, location, description)
3. File is downloaded / shared to the device's calendar app (Outlook, Google Calendar, Apple Calendar)

**Acceptance Criteria:**
- [ ] .ics file contains: VEVENT with DTSTART, DTEND, SUMMARY, LOCATION, DESCRIPTION
- [ ] Times include timezone information (VTIMEZONE or UTC offset)
- [ ] File is generated on-demand (not pre-generated) so it reflects the latest event details
- [ ] Works on iOS (opens in Calendar.app), Android (opens in default calendar), web (file download)

**Edge Cases:**
- Event with no end date -- .ics should still be valid (DTEND = DTSTART + 1 hour default?)
- Event with no location -- LOCATION field omitted
- .ics is inherently shareable -- document this for client awareness (attendees can forward invites)

## UC-6: Admin Views and Manages Attendees

**Actor:** Channel Admin or Editor
**Precondition:** Event exists, user has admin/editor role

**Main Flow:**
1. Admin opens the event card in CMS dashboard
2. Admin sees attendee management view:
   - Total attending count
   - Total waitlisted count
   - List of attendees with: name, email, department, position, status (ATTENDING/WAITLISTED), RSVP timestamp
3. Admin can export attendee list as CSV

**Acceptance Criteria:**
- [ ] Attendee list is paginated for large events
- [ ] CSV export includes: name, email, department, position, status, RSVP timestamp
- [ ] CSV uses streaming generation for large exports (>1000 attendees)
- [ ] Export restricted to admin/editor roles (contains PII)
- [ ] Deleted/banned users anonymized or excluded from export

**Future consideration (not v1):**
- Admin manually promotes a waitlisted user (by expanding capacity)
- Admin sends push notification to all attendees
- Admin sends email to all attendees

**Edge Cases:**
- User who attended is later deactivated/deleted from the organisation -- show as "Deactivated User" in admin view, anonymize in CSV
- Very large event (10,000+ attendees) -- pagination and streaming export are mandatory

## UC-7: Calendar View (Channel-Level)

**Actor:** Reader or Admin
**Precondition:** User has access to the channel

**Main Flow:**
1. User navigates to the channel's calendar view (accessible via dedicated tab or navigation)
2. Calendar displays all published events in the channel across all mixes
3. User can navigate by month/week
4. Tapping an event date/dot opens the event card detail

**Acceptance Criteria:**
- [ ] Dedicated GraphQL endpoint: `eventCardsByChannel(channelId, dateRange)` returns events across all mixes
- [ ] Endpoint enforces channel membership check -- user must have access to the channel (prevents IDOR)
- [ ] Calendar shows events as dots/markers on their start dates
- [ ] Supports month and week navigation
- [ ] Events from all mixes in the channel are aggregated (not just the current mix)
- [ ] Past events are visually distinct (greyed out)

**Edge Cases:**
- Day with many events (5+ events on same day) -- needs overflow/truncation UI
- All-day events vs. time-specific events -- both must render correctly
- Empty calendar month -- show empty state, not a blank grid

## UC-8: "My Events" Personal View

**Actor:** Reader
**Precondition:** User is ATTENDING or WAITLISTED for at least one event

**Main Flow:**
1. User navigates to "My Events" view (accessible from profile or dedicated nav)
2. View shows all events the user is attending or waitlisted for, across ALL channels
3. Events sorted by date (upcoming first)
4. Quick access to event details from each item

**Acceptance Criteria:**
- [ ] Dedicated GraphQL endpoint: `eventCardsByUser(page, size)` returns cross-channel results
- [ ] Shows event status per item (ATTENDING vs. WAITLISTED)
- [ ] Past events shown separately or filtered (toggle: upcoming / past / all)
- [ ] Works cross-channel (user sees events from all channels they have access to, scoped by userId -- this is a user-scoped query, not a channel-scan aggregation)
- [ ] Only shows events from organisations where the event feature flag is enabled
- [ ] Navigation placement: TBD with UX team before native app sprint. Candidates: profile section, dedicated bottom nav tab, or section within channel navigation.

**Edge Cases:**
- User loses access to a channel -- events from that channel disappear from "My Events"
- User with 100+ events -- pagination needed
- Empty state -- friendly message when user has no events

---

## UC-9: Push Reminders

**Actor:** System (automated)
**Precondition:** Event exists, has attendees, reminder timing is configured

**Main Flow:**
1. Scheduled background job checks for events starting within the configured reminder window (e.g., 24 hours, 1 hour)
2. System sends push notification to all ATTENDING users: "[Event Name] starts in [time]"
3. Deep-link in the notification opens the event card in the app

**Acceptance Criteria:**
- [ ] Uses existing push notification infrastructure (no new push system)
- [ ] Handles: event deleted before reminder fires, user unattended after schedule, event time changed
- [ ] Reminder timing is organisation-level setting for v1 (see ADR-3). Default: 24h + 1h before event start. Per-event override is Phase 2.
- [ ] Notification contains event title and time
- [ ] Deep-link opens the specific event card

---

## UC-10: Past Event State

**Actor:** System + Reader
**Precondition:** Event start date/time has passed

**Main Flow:**
1. System automatically transitions event to "past" state when event start time passes
2. Visual changes:
   - Cover image greyed out
   - "This event has ended" badge displayed
   - Attend/unattend button hidden
3. Comments remain open (acts as retrospective/feedback thread)
4. Event still appears in search results and feed (not deleted)
5. Event appears as past in calendar view and "My Events"

**Acceptance Criteria:**
- [ ] State transition is automatic (no admin action needed)
- [ ] No cron job needed for visual state -- calculated client-side from eventStartDate
- [ ] Comments, reactions, bookmarks still work on past events
- [ ] Past events remain searchable and browsable
- [ ] Admin can still access attendee list and export CSV for past events

# Part 3: Architecture Decisions

## ADR-1: Events as Cards in Mixes vs. Dedicated Event Feed

| Dimension | Option A: Card in Mixes (recommended) | Option B: Dedicated Event Feed Tab |
|-----------|--------------------------------------|-----------------------------------|
| **How it works** | Event is card type #12. Created inside any mix. Appears in feed alongside other cards. Calendar view aggregates all event cards in a channel. | Event Feed is a new top-level tab (like Bookmarks). Events created only in the Event Feed. Can be "promoted" to mixes as read-only copies. |
| **Pros** | Fits existing architecture. No new navigation concepts. Events appear where editors decide to put them. Reuses all card infrastructure (comments, reactions, tags, search). | Dedicated home for events. Clean separation. Filters and calendar are native to the tab. Solves the "where do I find all events?" problem by default. |
| **Cons** | Events scattered across mixes -- no single "all events" view without calendar feature. Requires calendar view (F5) to be useful. | New architectural concept. Doesn't fit Organisation > Channel > Mix > Card hierarchy cleanly. "Promoting" cards to mixes is a new sync pattern. More dev effort. |
| **Reuses existing code** | All card infrastructure, mix settings, feed rendering, search, tags | Requires new tab type, new creation flow, new sync mechanism |
| **Effort** | M (extends existing patterns) | XL (new concept end-to-end) |
| **Risk** | Low -- incremental extension | High -- new navigation, new data flow |

**Recommendation:** Option A. Events as card type #12 in mixes. The calendar view (F5) and "My Events" (F6) provide the aggregation that Option B gives for free, but without introducing a new architectural concept. Option B can be reconsidered later if event volume grows to the point where a dedicated tab is warranted.

**Decision for dev team:** Does the team see technical blockers with Option A that would push toward Option B? Specifically: is the `eventCardsByChannel` aggregation query performant enough to serve as the calendar data source?

## ADR-2: Event-Related Content (Future Scope)

Not in v1 scope. For future reference: when users want to post content related to events (photos, recaps, Q&A), the leading option is auto-generated event tags (low effort, uses existing tag infrastructure). More ambitious options include linked cards (linkedEventId field) or embedded mini-feeds in event detail views. Full decision record will be written when this enters scope.

## ADR-3: Reminder Timing Configuration

**Options:**
- A) Per-event configuration (admin sets reminder times when creating the event)
- B) Per-organisation default (global setting, e.g. "always remind 24h + 1h before")
- C) Hybrid (org default + per-event override)

**Recommendation:** Option B for v1 (simplest). Organisation-level default reminder timing. Per-event override (Option C) in Phase 2 if clients request it.

# Part 4: Open Questions for Dev Team

1. **Calendar query performance:** Can `eventCardsByChannel(channelId, dateRange)` scan across all mixes in a channel efficiently? Does this need a denormalized index or is the existing schema sufficient with a composite index on (channel_id, card_type, event_start_date)?

2. **Waitlist promotion reliability:** The background job for promoting waitlisted users when someone unattends -- what's the retry/failure strategy? If the promotion job fails, is the spot lost?

3. **Push reminder scheduling:** Should reminders use a polling-based scheduled job (check every N minutes for upcoming events) or event-driven scheduling (schedule a specific job when the event is created/updated)?

4. **Native app timeline:** iOS and Android need to render the new card type. What's the minimum native app release cycle to coordinate? Old versions hide the card entirely -- is that acceptable for the initial rollout period?

5. **Multi-timezone display:** Events stored in UTC with timezone offset. How does the frontend determine the user's timezone? Is this already solved for other timestamp displays?

6. **Capacity editing after publish:** If an admin changes capacity from 50 to 30 but 45 people are already attending, what happens? Current premise: no retroactive removal. Is this acceptable?

7. **AOK Plus executive channel problem:** Executives need to see events from both the general channel and the executive channel. "My Events" partially solves this (shows events across channels the user is attending). But for discovery of new events across channels, cross-channel aggregation (F15) is Phase 2. Is this acceptable for AOK Plus's initial rollout?

## Success Criteria

1. AOK Plus can create event cards, collect RSVPs, and export attendee lists within their existing channel structure
2. End users can discover events in the feed, RSVP with one tap, and add events to their personal calendar
3. Waitlist auto-promotion works reliably without manual admin intervention
4. Calendar view provides a channel-level overview of all upcoming events
5. Feature can be enabled/disabled per organisation via feature flag
6. Old app versions continue to work (event cards hidden, not broken)

## Dependencies

- Native app release cycle (iOS + Android must support new card type)
- Feature flag infrastructure (per-organisation toggle)
- Background job system for waitlist promotion and push reminders
- Existing push notification infrastructure
- Existing tag system (if F15 is included)
