Section 1b
Cancel Attendance Flow
What happens when a user taps "Attending" or "On Waitlist" to cancel. Includes confirmation to prevent accidental cancellation.
Use Case covered in this section
UC-4: User Cancels Attendance — Toggle off "Attending" or explicit cancel. If user was ATTENDING and waitlist exists, next waitlisted user auto-promoted via background job (FIFO). Promotion triggers push notification. Unattend blocked after event starts or registration deadline.
Why confirmation: Cancelling when a waitlist exists is not easily reversible -- the user's spot is immediately given to the next waitlisted person. Re-attending may result in being waitlisted.

Section 5
CMS: Create Event Card
Admin/Editor form in the CMS dashboard. Follows existing "Add Content" patterns with event-specific fields.
Use Case covered in this section
UC-1: Admin Creates an Event — Admin selects "Event" from "Add Content" in any mix. Fields: headline (required, 360 chars), description (rich text), start date/time with timezone (required), end date/time, location, cover image, capacity, registration deadline (defaults to event start), show-attendees toggle. Feature flag must be ON for Event type to appear in "Add Content".
Validations: Start must be future, end after start, deadline before/equal to start, capacity >= 1 if set.

Section 7 — Reference
Button State Matrix
All possible states for the attend button, mapped to conditions. Covers UC-3 (Attend), UC-4 (Cancel), UC-10 (Past).
Implementation notes from spec
Atomic capacity: UPDATE ... SET attendeeCount = attendeeCount + 1 WHERE attendeeCount < capacity prevents race conditions.
Debounce: Attend/unattend debounced at 1s minimum. Double-tap is idempotent.
Pessimistic UI: Wait for server confirmation before updating button state. On failure: inline error "Could not register. Try again."
Locking: Attend/unattend locked after event starts OR after registration deadline (whichever is earlier).
See full spec: Architecture Decisions #2, #5

Section 8 — Backend Only
Features Without Dedicated UI
These use cases and features are backend/infrastructure concerns with no dedicated screen. Listed here for completeness of the UC mapping.
UC-9: Push Reminders
View in Notion
Scheduled background job checks for events starting within the configured reminder window. Sends push notification to all ATTENDING users: "[Event Name] starts in [time]" with deep-link to event card. Uses existing push notification infrastructure.
Reminder timing: Organisation-level setting (default: 24h + 1h before event start). Per-event override is Phase 2.
Must handle: Event deleted before reminder, user unattended after scheduling, event time changed.
Open question: Polling-based job (check every N minutes) vs. event-driven scheduling (schedule job on create/update).
F9 Push Reminders
F13: Feature Flag per Organisation
View in Notion
Mandatory per-organisation feature flag. Controls: Event type visibility in "Add Content", event card rendering in feed, calendar view availability, My Events inclusion. Enables gradual rollout, kill switch, and client-by-client enablement.
F13 Feature Flag
F14: Backward Compatibility
View in Notion
Old native app versions (iOS/Android) that don't know the Event card type hide it entirely. Users on old versions won't see event cards until they update. No crash, no broken layout.
